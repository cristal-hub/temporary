**Главное правило реализовано:** достоверный снимок портфеля управляет текущим остатком позиции (`pos.quantity`); накопительное исполнение BUY-ордера (`lots_executed` / `entry_applied_lots` / `executed_lots`) управляет только учётом исполненных входных лотов. Величины не подменяют друг друга.

## 1. Краткая причина дефекта

`ExecutionMonitor.sync_recovery_quantity()` использовалась в двух принципиально разных ситуациях:

- **(А)** актуализация остатка RECOVERY-позиции по **достоверному снимку брокерского портфеля** (reconcile) — допустимо и увеличение, и уменьшение;
- **(Б)** повторная обработка **накопительного `lots_executed`** старой BUY-заявки (`register_executed_buy`, ветка существующей RECOVERY-позиции; а также `promote_recovery_positions` перед промоцией).

`lots_executed` заявки — накопительное исполнение этой заявки; `pos.quantity` — текущий остаток у брокера. Они расходятся, если оператор вручную продал часть позиции. Прежний код в ситуации (Б):

- вызывал `sync_recovery_quantity(existing, executed_lots)` и **слепо присваивал** `quantity := lots_executed` — повторный ответ старой заявки с `lots_executed = 8` «восстанавливал» 3 вручную проданных лота (остаток 5 → ошибочно 8);
- та же функция допускала **уменьшение** — устаревший ответ с меньшим `lots_executed` ошибочно уменьшал позицию;
- счётчики накопительного BUY-исполнения (`entry_applied_lots`/`executed_lots`) перезаписывались значением **остатка** позиции при каждой синхронизации по снимку;
- связь ордера с позицией по `entry_order_id` в RECOVERY-ветке не проверялась.

## 10. Оставшиеся ограничения и непроверенные сценарии

1. **Смешанная семантика `executed_lots` сохранена как есть** (по постановке — «сохранить существующую семантику, проверив все места использования»): в entry-пути (RECOVERY/OPEN, регистрация входа) — накопительное исполнение BUY; в пути закрытия (`resolve_closing` → CSV-запись в `process_closing`) — исполнение закрывающей SELL-заявки. Все места перечислены и не изменены; унификация — отдельная задача, к данному дефекту не относится.
2. **Ветка «догона счётчиков»** (`le == seen > applied`): разрыв между уже виденным у заявки исполнением и учтённым в позиции закрывается только счётчиками, количество не меняется (защита от восстановления проданных лотов). Логика покрыта code-review и реализована в общем пути `record_recovery_entry_lots`, но отдельного юнит-теста именно на эту ветку нет (в существующих тестах `seen == applied`).
3. **Противоречие при промоции** (`broker_le < baseline` в `promote_recovery_positions` → промоция отложена, UNCERTAIN в реестре): реализовано, но выделенного теста нет; существующие тесты промоции проходят.
4. **SHORT-RECOVERY с order_id**: промоция по отчёту входной заявки теперь явно запрещена (guard направления). Ранее она была возможна только при совпадении `le == quantity`; guard — прямое следствие удаления случайной защиты через знаковую проверку `sync_recovery_quantity`. Отдельного теста нет.
5. **Adopted-позиция + связанная заявка, чьё исполнение было уже видено, но продавалось до адопции**: дельта сверх `seen` не добавляется (защита реализована через `already_seen_lots` из реестра); сценарий частично покрыт `test_n4_no_resurrection_after_position_closed`, отдельного прямого теста нет.
6. **Прогон — песочница тестов, не боевой**: все тесты — проектные (FakeClient без сети); поведение с реальным брокером не проверялось (SANDBOX-only, торговые вызовы не выполнялись).
7. **Окончания строк** сохранены как у оригиналов (`execution.py` — CRLF, `main.py` и тест — LF): замена файлов drop-in.

## Приложение: карта вызовов и мутаций (проверка §6 постановки)

**`sync_recovery_quantity()` — единственное живое место вызова:** `main.reconcile()` (достоверный снимок портфеля: reconcile-сверка/адопция). Больше нигде не вызывается (обработка отчётов заявок переведена на `record_recovery_entry_lots`).

**Все места изменения `quantity` / `entry_applied_lots` / `executed_lots`:**

| Место | Величина | Правило |
|---|---|---|
| `execution.py: sync_recovery_quantity` | quantity; счётчики только при росте | снимок управляет остатком в обе стороны; счётчики не подменяются остатком |
| `execution.py: record_recovery_entry_lots` (новый) | quantity += только новые лоты; счётчики = le | накопительное исполнение конкретной BUY-заявки; база = max(applied, seen); le < базы — противоречие без изменений |
| `execution.py: apply_late_entry_lots` (не менялся) | quantity += дельта; счётчики = le | поздние лоты OPEN-позиции; SL/TP не пересчитываются; повторный ответ — no-op |
| `execution.py: resolve_closing` / `resolve_uncertain` / `reconcile`-закрытие (не менялись) | quantity по закрывающей заявке/сверке | прежняя семантика сохранена |
| `main.py: register_executed_buy` (регистрация новой позиции) | executed_lots = исполненное | прежнее поведение |

**Проверенные потоки:** стартовая сверка (`startup_recovery` → `register_executed_buy`), повторная обработка заявок (`poll_open_orders`), RECOVERY → OPEN (`promote_recovery_positions`), поздние исполнения OPEN, сохранение/загрузка state (счётчики — поля dataclass, сериализуются `asdict` автоматически; раунд-трип покрыт Тестом 3), идемпотентность повторных циклов (равенство — no-op: Тесты 1 и 3, `test_n2`, `test_n4`).
