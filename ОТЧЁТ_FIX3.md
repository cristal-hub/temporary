## Закрытие edge case: исполнение BUY без достоверного order_id

Репозиторий: `cristal-hub` (`/home/z/my-project/repo/`, ветка main, рабочее дерево
= состояние после FIX 2 + изменения FIX 3). Режим: только код + unit-тесты,
без запуска робота, без T-Invest API, без торговых операций, без commit/push.

## 1. Точная причина дефекта

В `main.py` проверка принадлежности исполнения активной позиции (защита FIX 2)
выполнялась только при **непустом** `order_id`:

```python
if (order_id and (not existing.entry_order_id
                  or str(order_id) != str(existing.entry_order_id))):
```

При `order_id=None`, `order_id=""` или `order_id="   "` условие `order_id and ...`
ложно — вся проверка пропускалась, и исполнение проваливалось в вызов
`apply_late_entry_lots(existing, executed_lots, order_id)`. В `execution.py`
метод допускает `order_id=None` и сам проверяет принадлежность аналогичным
образом (`if order_id and pos.entry_order_id and order_id != pos.entry_order_id`):
при пустом `order_id` проверка тоже пропускалась, и дельта
`le - entry_applied_lots` **применялась к уже существующей OPEN BUY-позиции**
(рост `quantity`, перезапись `entry_applied_lots`) **без какого-либо
подтверждения, что исполнение относится именно к этой позиции**.

Та же дыра существовала для RECOVERY-позиций: `record_recovery_entry_lots()`
с пустым `order_id` пропускал проверку принадлежности и добавлял дельту к
`quantity`. Оба пути нарушают главный принцип: *отсутствие идентификатора —
это неопределённость, а не разрешение применить исполнение*.

Дополнительно: при пустом `order_id` блок записи реестра
(`if ledger is not None and order_id:`) не выполнялся — ложный успешный
маркер не писался, но и диагностика не фиксировалась; событие исчезало
без следа.

### Почему в реестр (order_ledger) не пишется UNCERTAIN-запись

`record_uncertain()` адресуется `order_id`. Фиктивные идентификаторы
запрещены ТЗ (п.3). Запись с пустым/None-ключом либо создаёт фантомную
запись в индексе реестра (ключ `""`), либо (после перезапуска, при replay
`str(None)`→`"None"`) мёртвую запись, недоступную разрешению. Поэтому
использован безопасный механизм диагностики (`research_events.jsonl`) +
глобальный флаг `uncertain_state` — вариант, прямо предусмотренный ТЗ п.3.
Согласовано с существующей веткой «исполнение без FIGI» (ledger пишется
только при непустом order_id). Падение обработки исключено: в guard-ветке
реестр не вызывается вовсе.
