## 1. Этап A — READ ONLY: подтверждение дефектов

### Дефект №1 — ПОДТВЕРЖДЁН (воспроизведён на актуальном коде)

**Место:** `main.py`, `register_executed_buy()`, guard на строках 1076–1093 HEAD (в исправленной версии — строки ~1116–1190).

**Механизм дефекта:**
1. В `trading_cycle()` FILL-ветка: `ledger.record_sent(order_id, ..., executed_lots=sent_le, status_hint=sent_status_name)` (строка 2289 HEAD). При ответе брокера FILL с `lots_executed=N` `record_sent()` (`order_ledger.py`, строки 192–209) записывает в реестр ЗАПИСЬ СО СТАТУСОМ `"FILL"` и `executed_lots=N` — то есть терминальную.
2. Затем (строки 2480–2535 HEAD) запрашивается состояние заявки и вызывается `register_executed_buy(..., executed_lots=N)`.
3. Guard видит: `rec_pre.status == "FILL"` ∈ терминальных; `not monitor.has_active_position(figi)` — позиция ещё НЕ создана (её создание — единственная задача этого вызова); `executed_lots (N) <= recorded_le (N)`.
4. `return None` — первичная регистрация НЕ выполняется. Позиция не создаётся, событие `POSITION_OPENED` и Telegram-уведомление об открытии не отправляются. Позднее `reconcile()` усыновляет бумаги как RECOVERY без `entry_order_id`/цены входа.

**Пути, где срабатывает (все проверены на коде):**
- нормальная FILL-ветка `trading_cycle` сразу после `record_sent` (основной путь);
- ветка `state=None` после FILL (регистрация по данным post-ответа, строки 2481–2507);
- `startup_recovery()` для residual-заявок, исполнение которых не было применено (крах процесса между `record_sent` и регистрацией);
- поздний рост лотов терминальной заявки при вызове из веток с полными данными.

**Воспроизведение:** `record_sent(FILL, 5)` → `register_executed_buy(executed_lots=5)` → `None`, позиция отсутствует. После исправления — позиция создаётся (quantity=5, entry_order_id установлен).

**Причина по существу:** guard приравнивал «FILL в реестре» к «исполнение применено к локальной позиции». Это неверно: `record_sent()` пишет терминальный статус ДО регистрации позиции, а применение лотов происходит только внутри самого `register_executed_buy()`. Отсутствие активной позиции — не доказательство применения; наличие FILL в реестре — тоже.

## 2. Ответы на обязательные вопросы по execution.py (п.4 ТЗ)

1. **Хранение позиций:** `monitor.positions: Dict[str, TrackedPosition]` — ОДНА запись на FIGI.
2. **CLOSED-позиции:** сохраняются в памяти (`state=CLOSED` остаётся в dict) и находятся там, пока не перезаписаны.
3. **state.json:** `export_state()` сериализует ВСЕ записи, включая CLOSED; `_save_state()` пишет их в state.json; `_load_state()`/`import_state()` восстанавливают.
4. **Перезапись CLOSED:** ДА — `register()` и `register_recovery()` проверяют только `has_active_position()` (CLOSED не входит в ACTIVE_STATES), новая позиция полностью заменяет запись (`self.positions[figi] = pos`). Подтверждено воспроизведением.
5. **Потеря entry_order_id:** ДА — при перезаписи объект заменяется целиком, старый `entry_order_id` теряется (и из последующего state.json).
6. **Различение после перезапуска:** опиралось только на живую CLOSED-запись в monitor.positions. При перезаписи записи новой покупкой по тому же FIGI признак терялся — различить «старую закрытую сделку» и «новую незарегистрированную позицию» было невозможно.
7. **entry_applied_lots / trade_id:** `entry_applied_lots` — накопительное исполнение входной заявки, применённое к локальной позиции (заполняется при регистрации, догоняется `record_recovery_entry_lots`/`apply_late_entry_lots`, НЕ подменяется остатком снимка); `trade_id` — идентификатор сделки из SIGNAL, хранится в TrackedPosition и в реестре заявок.
8. **startup_recovery/reconcile:** `startup_recovery()` — проход по `ledger.open_orders()` (нетерминальные + residual); терминальные ПОЛНЫЕ FILL в него НЕ попадают, поэтому при крахе между `record_sent` и регистрацией позиция не восстанавливалась через заявки — только поздняя адопция `reconcile()` как RECOVERY (без entry_order_id/цены входа, промоция невозможна, контроль оператора).

**Доказанная необходимость минимального механизма сохранения признака закрытой сделки (п.4 ТЗ):**
Ослабление guard'а (FILL больше не доказательство применения) в сочетании с перезаписью CLOSED-записи открывало бы «воскрешение» закрытой сделки по позднему residual-отчёту после перезапуска: предыдущий guard блокировал такой случай условием `executed_lots <= recorded_le` (в т.ч. ложноположительно — ценой дефекта №1). Устранив ложноположительное срабатывание, необходимо сохранить истинную защиту. Минимальный механизм: компактный список `closed_entry_order_ids` (последние 200, FIFO) — пополняется при перезаписи CLOSED-записи и при экспорте state (все текущие CLOSED), сериализуется в state.json, восстанавливается при загрузке; обратная совместимость со старым state.json (отсутствие ключа → пустой список). Механизм внедрён в `execution.py` + `_save_state`/`_load_state` (`main.py`). Дополнительно для восстановительных сценариев добавлен второй проход `startup_recovery()`: терминальные FILL-заявки с исполнением и БЕЗ признака применения (reason не содержит «позиция зарегистрирована»/«исполнение применено») доводятся до регистрации через ту же единую точку; принадлежность к закрытым сделкам отсекает guard (entry_order_id / closed_entry_order_ids).

- При штатном разрешении RECOVERY (промоция) отправляется уведомление «RECOVERY разрешена» (`promote_recovery_positions`, строки 1883–1887 HEAD).
- Порядок «регистрация → сохранение state → уведомление» сохранён без изменений. Покрыто тестами s8/s8b (уведомление проверяет существование позиции в момент отправки; без регистрации уведомлений нет).

## 5. Риски совместимости

1. **state.json:** новый ключ `closed_entry_order_ids`. Старый state.json читается корректно (пустой список — тест roundtrip). Новый state.json старой версией робота игнорируется (дополнительный ключ в dict безвреден).
2. **Привязка RECOVERY:** усыновлённые reconcile-позиции (trade_id пуст) больше НЕ привязываются к заявкам автоматически — по требованию ТЗ (нельзя связывать по одному FIGI). Путь промоции для них открывается только при подтверждённой принадлежности (совпадении trade_id) или оператором/сверкой. Это консервативное поведение, исключающее применение чужого исполнения.
3. **Второй проход startup_recovery:** на старых state.json (без closed_entry_order_ids) заявки, зарегистрированные предыдущими версиями кода, защищены маркером reason («позиция зарегистрирована»/«исполнение применено») — они не переобрабатываются. Терминальные записи реестра, никогда не проходившие регистрацию, будут зарегистрированы штатно (это и есть цель — краховое восстановление).
4. **UNCERTAIN-поведение не ослаблено:** P0-5 гейт сохранён; в новом коде UNCERTAIN-запись пишется только добавлением (append-only), перезаписи терминальным статусом нет.
5. **Тестовая среда:** в окружении аудита SDK `t-tech-investments==1.51.0` недоступен в публичном PyPI (проект на PyPI — только 0.3.x); тесты выполнены с минимальной заглушкой `t_tech.invest` (только перечисления/utils, без сетевых вызовов — unit-тесты используют FakeClient). Значения перечислений соответствуют документации T-Invest API и маппингу `main.py`.

## 9. ДОПОЛНИТЕЛЬНЫЙ ЭТАП — целостность реестра и state.json

Постановка (4 пункта): (1) убрать небезопасное ограничение архива 200 закрытых заявок; (2) не записывать в ledger подтверждение регистрации, если state.json не сохранён; (3) при несовпадении entry_order_id в активной RECOVERY-позиции явно фиксировать UNCERTAIN, а не отмечать чужую заявку как обработанную; (4) добавить тесты на эти три ситуации и повторить полный прогон.

### 9.1 Что изменилось

**П.1 — архив закрытых заявок без лимита (`execution.py`).**
Удалены константа `MAX_CLOSED_ENTRY_ORDER_IDS = 200` и ВСЕ три обрезки (архивация при перезаписи CLOSED-записи, `export_state()`, `import_state()`). Обоснование опасности лимита: после 200 закрытий FIFO вытеснял признаки СТАРЫХ закрытых сделок — поздний residual-отчёт вытесненной заявки больше не распознавался guard'ом (`evidence_closed_entry`) и «воскрешал» позицию, а перезапись/отсутствие CLOSED-записи делала это неотличимым от первичной регистрации. Каждая запись архива — только короткий `order_id`, рост файла state.json пренебрежим (сотни сделок ≈ единицы КБ), поэтому ограничение не заменяется, а снято. Обратная совместимость: старый state.json без ключа — пустой список (как и прежде).

**П.2 — подтверждение регистрации только после сохранения state.json (`main.py`, `register_executed_buy()`).**
Ключевой механизм: reason-маркеры «позиция зарегистрирована» / «исполнение применено» в реестре используются вторым проходом `startup_recovery()` как признак «применение уже учтено — не переобрабатывать». Раньше подтверждение писалось независимо от результата сохранения: при сбое записи state.json реестр подтверждал то, чего нет в персистентном состоянии, и при перезапуске позиция терялась (маркер заставлял восстановление пропустить заявку). Теперь:
- *первичная регистрация*: `ledger.record_status(... "позиция зарегистрирована")` выполняется только при `state_saved == True`; при сбое — только запись ошибки в лог (ошибка уже зафиксирована `_save_state_checked`: `STATE_SAVE_FAILED` + блокировка новых входов). Незаписанное подтверждение оставляет заявку доступной доведению до регистрации при перезапуске — штатному сценарию восстановления после краха между `record_sent` и регистрацией (тест `test_s9b` semantics);
- *поздний рост (ветка `has_active_position`)*: сохранение перенесено ДО записи подтверждения; подтверждение «позднее исполнение применено к позиции» пишется только при успешном сохранении. При сбое сохранения пишется UNCERTAIN-запись (`client.uncertain_state` + `record_uncertain`): простое НЕнаписание здесь недостаточно — прежнее подтверждение регистрации маскировало бы несохранённую дельту при перезапуске; UNCERTAIN держит заявку нетерминальной (доступной опросу/сверке), и дельта применяется повторно после перезапуска (подтверждено тестом: перезапуск 5 лот. → poll → 8 лот.).

**П.3 — несовпадение entry_order_id в активной RECOVERY (`main.py`, `register_executed_buy()`).**
Новая ветка `elif` сразу после блока привязки: активная RECOVERY с уже заданным `entry_order_id` и отчёт ДРУГОЙ заявки (`str(order_id) != str(existing.entry_order_id)`) → `client.uncertain_state = True` + UNCERTAIN-запись реестра для чужой заявки, исполнение НЕ применяется, позиция не перепривязывается, терминальный статус чужой заявке НЕ пишется (раньше отчёт проваливался в общую ветку идемпотентности и помечался «позиция уже зарегистрирована — идемпотентность», т.е. чужая заявка отмечалась обработанной без применения её исполнения). Совпадение `trade_id` перепривязку не выполняет — позиция уже связана с другой заявкой. Отчёт СВОЕЙ заявки (совпадение `entry_order_id`) продолжает штатно применять рост cumulative (контрольный тест от перегиба).

**Сознательно НЕ расширено (минимальность правок):** аналогичная ветка идемпотентности для активной OPEN-позиции (поздний отчёт чужой заявки при `apply_late_entry_lots`-отказе) сохраняет прежнее поведение — постановка п.3 ограничена RECOVERY-позицией. Отмечено как кандидат на следующую итерацию, поведение не изменялось.
